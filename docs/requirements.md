# SourceTrace requirements (v0.1)

## Problem

AI tools can turn lecture slides into a knowledge tree in seconds, but the result is not trustworthy by default: a definition may be wrong, a relationship may be invented, and important material may be left out. SourceTrace checks an AI-generated knowledge tree against the original source images and explains every problem it finds with traceable evidence.

## Deliverable

SourceTrace is an auditing capability packaged as an Agent Skill (`source-trace/` with a `SKILL.md`), so any tool that supports Agent Skills, such as Claude Code or Codex, can invoke it. Its core is evidence extraction, knowledge mapping and bidirectional auditing.

It must not stop at "this knowledge point might be incorrect". Every finding answers three questions:

1. **Why** is this knowledge point problematic?
2. **Where** is the source material (file, page, snippet)?
3. **What** is the basis for the claim (the evidence IDs it rests on)?

## Inputs

| Input | Format | Notes |
|-------|--------|-------|
| Source material | PNG / JPG images | The single source of truth for v0.1, e.g. exported slides or screenshots. One image is one page. |
| Knowledge tree | JSON, see `source-trace/schemas/knowledge-tree.schema.json` | Generated by another AI tool. Treated as a claim, never as fact. |

### Language

Slides and trees may be in Chinese or English. Evidence quotes the source in its original language. The report is written in the language of the slides unless the user asks for another.

### Vocabulary

Node `kind` and edge `relation` come from small fixed lists, so relationships can be audited precisely. Trees from other tools may need their values mapped onto these first.

| Field | Allowed values |
|-------|----------------|
| `kind` | `concept`, `method`, `task`, `example`, `fact` |
| `relation` | `includes`, `is-a`, `part-of`, `example-of`, `causes`, `depends-on`, `uses`, `contrasts-with`, `related-to` |

## Workflow

SourceTrace runs six stages:

```
Source images (PNG/JPG) + AI-generated knowledge tree
  1. Source ingestion        identify pages, text, tables, graphics and key information
  2. Evidence extraction     evidence list with unique IDs, page, original text and location
  3. Knowledge mapping       tree → discrete knowledge points (nodes) and relationships (edges)
  4. Bidirectional audit     tree → evidence (is it supported?) and evidence → tree (is anything missing?)
  5. Conflict detection      classify each problem and assign a risk level
  6. Audit report            report.md (for people) + audit.json (for tools)
```

### 1. Source ingestion

Read each source image and identify its pages, text, tables, graphics and key information. v0.1 accepts PNG/JPG only; PPT and PDF sources are planned for later and can be exported to images in the meantime.

The agent reads the images with its own vision; there is no OCR step. This needs no install and handles diagrams and tables, at the cost of small differences between runs. Each evidence item's `certainty` records how confident the reading is, so unclear content is flagged rather than guessed.

### 2. Evidence extraction

Each piece of content in a source image becomes one evidence item (`source-trace/schemas/evidence.schema.json`) with a unique `evidence_id`, page number, original text and location, so every finding can cite it. Locations only need to be practical for v0.1: page (image) number plus a text snippet. Precise image coordinates are out of scope.

All items are collected in `evidence-index.json` (`source-trace/schemas/evidence-index.schema.json`), together with the list of sources from `validate_input.py`. The extraction rules are in `source-trace/references/evidence-extraction.md`:

- One item per slide title, bullet, table row and diagram relationship, so that each node and edge can be matched to specific items.
- Text is quoted verbatim in its original language; tables and diagrams use fixed transcription formats.
- Everything is extracted, including non-knowledge text such as homework. Deciding what is significant is the audit's job.
- `low` certainty evidence cannot reject a tree item on its own.

`source-trace/scripts/validate_evidence.py` checks the index:

| Check | Level |
|-------|-------|
| Index matches the schema | error |
| Evidence IDs are unique | error |
| Source IDs and pages are unique, and pages run 1 to n | error |
| Every item cites a listed source, with that source's page | error |
| Every source has at least one evidence item | warning |
| Items with `low` certainty are listed | warning |

### 3. Knowledge mapping

The tree is first checked for structural problems, then split into two kinds of reviewable objects, audited separately:

- **Node:** is the knowledge point itself correct (label and definition)?
- **Edge:** is the relationship between two knowledge points correct?

These are separate because a node can be correct while its relationship to another node is wrong. For example, "Supervised Learning" and "Unsupervised Learning" can both be well defined while `Supervised Learning —includes→ Unsupervised Learning` is false.

`source-trace/scripts/validate_input.py` runs the schema and the checks JSON Schema alone cannot express. Errors stop the audit; warnings are reported but do not.

| Check | Level |
|-------|-------|
| Tree matches the schema, including a supported `schema_version` | error |
| Node and edge IDs are unique | error |
| Every edge's `source` and `target` refer to an existing node | error |
| No edge points from a node to itself | error |
| Each image exists, is PNG/JPG, and its content really is that format | error |
| Image file names are unique (the name becomes `source_id`) | error |
| The same source, relation and target appear in only one edge | warning |
| Every node has at least one edge (when there is more than one node) | warning |
| All linked nodes form one connected tree, not several separate parts | warning |

Images are numbered as pages in natural file-name order, so `slide-2.png` comes before `slide-10.png`.

### 4. Bidirectional audit

- **Tree → source:** is each node and edge supported by evidence? This catches wrong or invented content.
- **Source → tree:** is each significant piece of evidence represented in the tree? This catches omissions.

### 5. Conflict detection

Each problem is classified into one category:

| Category | Meaning | Example |
|----------|---------|---------|
| `conceptual-error` | A node's definition contradicts the source. | "Supervised learning does not require labels." |
| `incorrect-relationship` | An edge contradicts the source, even if both nodes are correct. | Unsupervised Learning —includes→ Regression |
| `unsupported-expansion` | Content not found in the source, even if true in general. | A "Deep Learning" node from slides that never mention it |
| `overgeneralization` | Supported content stretched beyond what the source says. | "Every unsupervised task is clustering." |
| `ambiguous` | Content too vague or uncertain to confirm or reject. | "Feedback: the signal a model learns from" |
| `omission` | Significant source content missing from the tree (from the source → tree direction). | Dimensionality reduction left out |

The category is chosen with a fixed decision order (`source-trace/references/audit-rules.md`), so that two runs reach the same answer. The main boundary rule is the **qualifier test**: if deleting the absolute or widening part of a claim (总是, 最…, only, every …) leaves a supported claim, it is `overgeneralization`, even when another page contradicts the absolute version. A term the source mentions but never defines is `ambiguous`; a term the source does not mention is `unsupported-expansion`. Node `kind` is not audited in v0.1.

Each finding also gets a risk level: `high`, `medium` or `low`. Each category has a default; the agent may raise or lower it for a specific finding, but must give a `risk_reason` (e.g. an omission of the course's central concept is raised to high).

| Default risk | Categories |
|--------------|------------|
| `high` | `conceptual-error`, `incorrect-relationship` |
| `medium` | `unsupported-expansion`, `overgeneralization`, core omissions |
| `low` | `ambiguous`, supporting-detail omissions |

Omissions come in two tiers, both always reported: **core** (topics in titles or the agenda, defined terms, stated rules, table rows, diagram relationships) and **supporting details** (when to use a method, notation legends, properties of a concept already in the tree). Examples in parentheses and administrative text such as homework are never reported.

These rules were set after a consistency check (3 runs on model-eval, `tests/consistency/model-eval/summary.md`) showed the only disagreements were at exactly these two boundaries.

### 6. Audit report

| File | Audience | Content |
|------|----------|---------|
| `report.md` | People | Summary and findings, each with its category, risk level, reason, evidence references and a recommended revision. |
| `audit.json` | Tools and tests | The same findings in machine-readable form. |

## Out of scope for v0.1

- Sources other than PNG/JPG images (PPTX, PDF, video, web). Slides can be exported to images first.
- Precise image or bounding-box coordinates.
- Automatically fixing the tree. SourceTrace reports problems and does not rewrite the tree.
- OCR. Text is read by the agent's vision (see Source ingestion).

## Dependencies

`validate_input.py` needs `jsonschema` (`pip install jsonschema`), so the schema files stay the single source of truth for the rules.

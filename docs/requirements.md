# SourceTrace requirements (v0.1)

## Problem

AI tools can turn lecture slides into a knowledge tree in seconds, but the result is not trustworthy by default: a definition may be wrong, a relationship may be invented, and important material may be left out. SourceTrace checks an AI-generated knowledge tree against the original source images and explains every problem it finds with traceable evidence.

## Deliverable

SourceTrace is an auditing capability packaged as an Agent Skill (`source-trace/` with a `SKILL.md`), so any tool that supports Agent Skills, such as Claude Code or Codex, can invoke it. Its core is evidence extraction, knowledge mapping and bidirectional auditing.

It must not stop at "this knowledge point might be incorrect". Every finding answers three questions:

1. **Why** is this knowledge point problematic?
2. **Where** is the source material (file, page, snippet)?
3. **What** is the basis for the claim (the evidence IDs it rests on)?

## Inputs

| Input | Format | Notes |
|-------|--------|-------|
| Source material | PNG / JPG images | The single source of truth for v0.1, e.g. exported slides or screenshots. One image is one page. |
| Knowledge tree | JSON, see `source-trace/schemas/knowledge-tree.schema.json` | Generated by another AI tool. Treated as a claim, never as fact. |

### Language

Slides and trees may be in Chinese or English. Evidence quotes the source in its original language. The report is written in the language of the slides unless the user asks for another.

### Vocabulary

Node `kind` and edge `relation` come from small fixed lists, so relationships can be audited precisely. Trees from other tools may need their values mapped onto these first.

| Field | Allowed values |
|-------|----------------|
| `kind` | `concept`, `method`, `task`, `example`, `fact` |
| `relation` | `includes`, `is-a`, `part-of`, `example-of`, `causes`, `depends-on`, `uses`, `contrasts-with`, `related-to` |

## Workflow

SourceTrace runs six stages:

```
Source images (PNG/JPG) + AI-generated knowledge tree
  1. Source ingestion        identify pages, text, tables, graphics and key information
  2. Evidence extraction     evidence list with unique IDs, page, original text and location
  3. Knowledge mapping       tree → discrete knowledge points (nodes) and relationships (edges)
  4. Bidirectional audit     tree → evidence (is it supported?) and evidence → tree (is anything missing?)
  5. Conflict detection      classify each problem and assign a risk level
  6. Audit report            report.md (for people) + audit.json (for tools)
```

### 1. Source ingestion

Read each source image and identify its pages, text, tables, graphics and key information. v0.1 accepts PNG/JPG only; PPT and PDF sources are planned for later and can be exported to images in the meantime.

The agent reads the images with its own vision; there is no OCR step. This needs no install and handles diagrams and tables, at the cost of small differences between runs. Each evidence item's `certainty` records how confident the reading is, so unclear content is flagged rather than guessed.

### 2. Evidence extraction

Each piece of content in a source image becomes one evidence item (`source-trace/schemas/evidence.schema.json`) with a unique `evidence_id`, page number, original text and location, so every finding can cite it. Locations only need to be practical for v0.1: page (image) number plus a text snippet. Precise image coordinates are out of scope.

All items are collected in `evidence-index.json` (`source-trace/schemas/evidence-index.schema.json`), together with the list of sources from `validate_input.py`. The extraction rules are in `source-trace/references/evidence-extraction.md`:

- One item per slide title, bullet, table row and diagram relationship, so that each node and edge can be matched to specific items.
- Text is quoted verbatim in its original language; tables and diagrams use fixed transcription formats.
- Everything is extracted, including non-knowledge text such as homework. Deciding what is significant is the audit's job.
- `low` certainty evidence cannot reject a tree item on its own.

`source-trace/scripts/validate_evidence.py` checks the index:

| Check | Level |
|-------|-------|
| Index matches the schema | error |
| Evidence IDs are unique | error |
| Source IDs and pages are unique, and pages run 1 to n | error |
| Every item cites a listed source, with that source's page | error |
| Every source has at least one evidence item | warning |
| Items with `low` certainty are listed | warning |

### 3. Knowledge mapping

The tree is first checked for structural problems, then split into two kinds of reviewable objects, audited separately:

- **Node:** is the knowledge point itself correct (label and definition)?
- **Edge:** is the relationship between two knowledge points correct?

These are separate because a node can be correct while its relationship to another node is wrong. For example, "Supervised Learning" and "Unsupervised Learning" can both be well defined while `Supervised Learning —includes→ Unsupervised Learning` is false.

`source-trace/scripts/validate_input.py` runs the schema and the checks JSON Schema alone cannot express. Errors stop the audit; warnings are reported but do not.

| Check | Level |
|-------|-------|
| Tree matches the schema, including a supported `schema_version` | error |
| Node and edge IDs are unique | error |
| Every edge's `source` and `target` refer to an existing node | error |
| No edge points from a node to itself | error |
| Each image exists, is PNG/JPG, and its content really is that format | error |
| Image file names are unique (the name becomes `source_id`) | error |
| The same source, relation and target appear in only one edge | warning |
| Every node has at least one edge (when there is more than one node) | warning |
| All linked nodes form one connected tree, not several separate parts | warning |

Images are numbered as pages in natural file-name order, so `slide-2.png` comes before `slide-10.png`.

### 4. Bidirectional audit

- **Tree → source:** is each node and edge supported by evidence? This catches wrong or invented content.
- **Source → tree:** is each significant piece of evidence represented in the tree? This catches omissions.

### 5. Conflict detection

Each problem is classified into one category:

| Category | Meaning | Example |
|----------|---------|---------|
| `conceptual-error` | A node's definition contradicts the source. | "Supervised learning does not require labels." |
| `incorrect-relationship` | An edge contradicts the source, even if both nodes are correct. | Unsupervised Learning —includes→ Regression |
| `unsupported-expansion` | Content not found in the source, even if true in general. Scope `whole` for an absent term or relationship; scope `detail` for one added detail of an otherwise supported definition. | A "Deep Learning" node from slides that never mention it (whole); "有放回" in a bootstrap definition the source does not state (detail) |
| `overgeneralization` | Supported content stretched beyond what the source says. | "Every unsupervised task is clustering." |
| `ambiguous` | Cannot verify: the source only names the term and never explains it, or the evidence is unreadable. Shown as "资料未定义 / 无法核验". | "Feedback: the signal a model learns from" when Feedback is only a table header |
| `omission` | Significant source content missing from the tree (from the source → tree direction). | Dimensionality reduction left out |

The category is chosen with a fixed decision order (`source-trace/references/audit-rules.md`), so that two runs reach the same answer. The main boundary rule is the **qualifier test**: if deleting the absolute or widening part of a claim (总是, 最…, only, every …) leaves a supported claim, it is `overgeneralization`, even when another page contradicts the absolute version. A term the source mentions but never defines is `ambiguous`; a concept the source neither names nor describes is `unsupported-expansion`. Node `kind` is not audited in v0.1.

Two more rules came from the first review on real content (`tests/fixtures/wiki-ml-zh/audit-run-1/REVIEW.md`):

- **Gather all evidence before deciding:** text, tables and figures on every page, combined across pages. A finding of "cannot be checked" is only valid after that.
- **Contradiction test:** a conceptual error needs a contradiction in meaning. If the tree's statement and the source's can both be true at once, it is not one, however opposite the wording looks (e.g. a Bayesian network represents both dependencies and conditional independencies).

The owner's review of the second run (`tests/fixtures/wiki-ml-zh/audit-run-2/COMPARISON.md`) set the boundaries of the `detail` scope:

- **An explanation of the term is not a detail:** a part of a definition is a separate claim only if it could be false while the rest is true. "过度适应训练数据" for 过拟合 explains the term itself and is supported.
- **A class defined from one instance is a detail:** a general definition of 集成学习, when the source only explains random forest, is `detail` / low.
- **Only the unsupported fragment is the finding:** a non-contradicting difference in wording (预测误差 vs 泛化误差) goes into the recommendation as optional wording.
- **A method introduced in a paragraph about a field supports `uses`:** but only when it is the same paragraph, the field is its subject, and the method's stated purpose is part of what the field does.
- **Recommendations add no claims** that neither the tree nor the source makes.

The owner's review of the first run on a second article (`tests/fixtures/wiki-dt-zh/audit-run-1/REVIEW.md`) added:

- **A narrower or more cautious claim that the source implies is supported:** this mirrors the qualifier test. Widening a claim is a finding; narrowing it ("在分类时", "某些", "通常") is not.
- **A different word for a different property is a detail** (多路划分 vs the source's 多层分裂), while a different word for the same thing is not (预测误差 vs 泛化误差).
- **A node with a compatible definition covers the source's definition:** only the parts the tree lacks, such as a symbol legend, are omissions.
- **Limitations sections are read sentence by sentence,** because their statements are easy to miss as omissions.

The scale test (`tests/fixtures/sl-algos-zh/RESULTS.md`) added rules from the owner's decisions and from questions both agents raised:

- **A spelled-out name is not `ambiguous`:** question 7 applies the label test first. A definition that could not be false while the term is true (随机搜索 "随机采样若干组超参数进行评估") is supported even when the source only names the term.
- **A slide title does not define a class:** a 神经网络 definition built from a slide that only describes 多层感知机 is a `detail` finding.
- **Slide order supports no relationship:** a 核方法 slide after the SVM slide, which never names SVM, does not support 支持向量机 uses 核函数. Only the agenda rule lets structure state a relationship.
- **A finding covers only the content it is about,** so whether an omission is reported no longer depends on which evidence a finding cites. A topic whose members are all in the tree is not an omission.
- **Bullets are split when their parts can be cited separately,** for different concepts or different tree items, instead of "only if unrelated".
- **No matching relation:** when the correct relationship has no relation value (e.g. "mitigates"), recommend deleting the edge and stating it in a definition, not `related-to`. When the relation is right and only an end node is wrong, keep the relation and correct the node. `is-a` from a method to a task reads as "is a method for".

The image-quality test (`tests/fixtures/model-eval-occluded/RESULTS.md`) added:

- **Partly unreadable evidence** is split into a readable item and a `low` item with the placeholder ［无法辨认］. Hidden text is never filled in from the agent's own knowledge.
- **Working files** (drafts, helper scripts, enlarged crops) go in a `work/` folder inside the output folder.

The owner's decisions on a third article (`tests/fixtures/wiki-nb-zh/REVIEW.md`) added:

- **The concept counts, not the word:** a label from outside the source (词袋表示, 概率平滑修正) is supported when the source describes what it names. Only a claim the name adds, such as a specific formula, is checked as a `detail`.
- **Web pages and documents:** overlapping screenshots are extracted once; site menus and banners are skipped; a navigation box can back up the article's text but never supports an item or creates an omission on its own.
- **Formulas** are written out as linear Unicode text, exactly as printed.
- **Problems in the source itself** (contradictions, slips) are quoted as printed, judged by the more specific evidence, explained in the affected item's `reason`, and listed in the final message. They are not findings about the tree, and they need no new category.
- **Omission tiers:** a rule or caveat about a concept that has a node is a supporting detail; history, applications, other names and comparisons are supporting background. A missing claim appears in only one omission.
- **Recommendations are checked like findings:** they keep the source's conditions and never copy a source sentence that other evidence in the source contradicts.

Each finding also gets a risk level: `high`, `medium` or `low`. Each category has a default; the agent may raise or lower it for a specific finding, but must give a `risk_reason` (e.g. an omission of the course's central concept is raised to high).

| Default risk | Categories |
|--------------|------------|
| `high` | `conceptual-error`, `incorrect-relationship` |
| `medium` | `unsupported-expansion` (whole), `overgeneralization`, core omissions |
| `low` | `unsupported-expansion` (detail), `ambiguous`, supporting-detail omissions |

Omissions come in two tiers, both always reported: **core** (topics in titles or the agenda, defined terms, stated rules, table rows, diagram relationships) and **supporting details** (when to use a method, notation legends, properties of a concept already in the tree, and background such as history and applications). Examples in parentheses and administrative text such as homework are never reported.

These rules were set after a consistency check (3 runs on model-eval, `tests/consistency/model-eval/summary.md`) showed the only disagreements were at exactly these two boundaries.

### 6. Audit report

| File | Audience | Content |
|------|----------|---------|
| `report.md` | People | Summary, findings, source notes and omissions (each with ID, category, risk, reason, evidence with page and quote, and a recommended revision), structure warnings, and the confirmed items. Source notes are the `detail` findings, in a folded section after the other findings, because they mark a gap in the source rather than an error. |
| `audit.json` | Tools and tests | A verdict for every node and edge, the omissions, the summary and structure warnings (`source-trace/schemas/audit.schema.json`). |

The agent writes only its judgments (`items` and `omissions`). `source-trace/scripts/build_report.py` does everything that can be computed:

| Step | Detail |
|------|--------|
| Check the audit | Schema; exactly one verdict per node and edge; every evidence ID exists in the index; a supported item has no finding fields; `risk_reason` whenever a risk differs from the default (errors). A rejection that rests only on `low`-certainty evidence (warning). |
| Complete `audit.json` | Adds `summary`, `structure_warnings` (from the tree) and `finding_id`s F-001, F-002, … in report order. |
| Generate `report.md` | Findings, then source notes, then omissions; each sorted by risk, then lowest cited page, then tree order. The summary counts problems, source notes and omissions (core and supporting) separately, and its top-three list leaves out source notes and low-risk items. Evidence quotes are shown in full. Quotes come from the evidence index. Chinese or English, detected from the slides or set with `--lang`. |

On any error nothing is written, and the agent fixes `audit.json` and reruns. Running it again on a finished audit gives the same files.

## Out of scope for v0.1

- Sources other than PNG/JPG images (PPTX, PDF, video, web). Slides can be exported to images first.
- Precise image or bounding-box coordinates.
- Automatically fixing the tree. SourceTrace reports problems and does not rewrite the tree.
- OCR. Text is read by the agent's vision (see Source ingestion).

## Dependencies

`validate_input.py` needs `jsonschema` (`pip install jsonschema`), so the schema files stay the single source of truth for the rules.
